# 架构说明

## 逻辑分层

1. **交互层**：React 工作台、语义管理、分析资产、质量运营和审计页面。
2. **控制面**：OIDC、工作区、RBAC/ABAC、审计、配置、任务状态与评测事实。
3. **语义面**：版本化数据集、指标、维度、关系、同义词与数据质量状态。
4. **查询内核**：受限 QuerySpec → 语义校验 → 权限重写 → SQLGlot AST → 独立只读复核。
5. **执行面**：方言连接器、超时/配额、受控缓存、异步导出和报表。
6. **模型面**：企业内网 OpenAI 兼容端点，只允许生成结构化计划和有结果依据的解释。

## 基础设施职责

- PostgreSQL：控制面、任务事实源和审计；不是被查询业务数据库的替代品。
- Redis：短期缓存和任务协调；不是权限事实或任务完成事实。
- Milvus：语义向量检索的增强组件，故障时核心查询可降级运行。
- MinIO：私有上传和导出制品；下载必须重新鉴权。

## 当前代码边界

已实现：问数主链路（规划 → 编译 → 只读执行 → 摘要 / 图表 / 依据）、手动与自然语言两个入口、控制面（迁移、OIDC 令牌校验、工作区 RBAC、只能追加的审计）、开发登录与演示数据、前端问数界面。

尚未实现：浏览器端 SSO 登录、控制面 RLS、任务事实源、多关系 JOIN、真实企业数据源接入（目前仅 PostgreSQL 演示表）、Milvus 检索、多轮对话、仪表盘与报表。不能由目录名称推断这些已经完成。

## 问数请求的数据流

`POST /workspaces/{id}/ask` 接受 `question`（自然语言）或 `query`（结构化）二选一：

1. 校验 `query:run` 权限（查看者拒绝，非成员 404，均写审计）。
2. 解析服务端授权策略（`resolve_policy`），得到可见的指标与维度。
3. 自然语言：规划器把问题 + 可见目录 + 维度取值发给内网模型，要求输出受限 QuerySpec，校验失败时修复一次。
4. 编译（`compile_query`）：策略先行，行过滤在基础子查询里，用户过滤与聚合在外层。
5. 独立只读复核 → 只读事务 + 语句超时执行 → 多取 1 行判断截断。
6. 生成摘要、图表建议和查询依据，写入审计，返回。

模型只出现在第 3 步，且它的输出在进入第 4 步之前必须通过结构化校验和语义校验；模型永远没有机会提交 SQL。

## 授权模型

- 身份来自 OIDC 令牌的 `(iss, sub)`，首次请求时在 `users` 表建档。
- 工作区角色逐级包含：查看者（读工作区与资产）→ 分析师（问数、写资产、导出）→ Steward（管理语义）→ 工作区管理员（数据源、成员、审计）。
- 组织管理员可管理所有工作区的成员和审计，但**不会**因此获得任何工作区的数据权限，需要以成员身份被授予数据角色。
- 不可见的工作区一律返回 404，避免泄露其存在；每次拒绝都写入审计。
- 业务改动与描述它的审计记录在同一事务中提交；拒绝记录使用独立事务，确保请求失败时仍被保留。

## 可靠性原则

PostgreSQL 中保存任务状态机、幂等键、租约、心跳与 outbox。worker 可以重试，但副作用必须幂等。缓存键包含工作区、规范化 QuerySpec、语义版本、数据源/schema 版本、权限策略指纹和新鲜度要求。
